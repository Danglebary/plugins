# Every test assertion can fail

## Goal

On bash 3.2 — the only bash macOS ships, and the one both suites run under — a failing `[[ ]]` inside a function neither trips `errexit` nor fires the ERR trap. A bats test is a function, so only its **final** command decides pass/fail: every earlier `[[ ]]` assertion fails silently. Twenty-six of the sixty-seven `[[ ]]` assertions across `contract-tamper.bats` and `materialize-diff.bats` are inert, including both non-final assertions of the test that pins base-relative line numbering. This ticket makes every assertion in both suites able to fail, and reports honestly on any that turn out to have been passing only because they never ran. Out of scope: adding coverage for behaviors the suites don't already claim to test — this is about making existing claims real, not making new ones.

## Acceptance criteria

- [ ] Every assertion in `contract-tamper.bats` and `materialize-diff.bats` fails its test when the asserted condition is false, regardless of position in the test body.
- [ ] A deliberately falsified assertion in a non-final position is demonstrated to fail the suite, and the demonstration is reverted — the enforcement is shown, not assumed.
- [ ] Any assertion that fails once enforced is reported to the user with its finding — whether the assertion was wrong or the code is — and resolved as its own decision, never silently rewritten to match current behavior.
- [ ] Assertions that compare against fixture text containing glob metacharacters (`[ ]` checkboxes, `*`, `?`) match that text literally.
- [ ] The reason the bare form is unreliable is recorded next to the helpers, so a future contributor doesn't "simplify" them back to `[[ ]]`.
- [ ] Both suites pass in full.

## Implementation notes

Ticket 002 added `assert_output_contains` / `refute_output_contains` to `contract-tamper.bats` and used them for its own tests only; the rest of that file and all of `materialize-diff.bats` still use the bare form. Reuse those helpers rather than introducing a second mechanism — but note they only cover substring checks on `$output`. The pre-existing suite also asserts with interior wildcards (`*"SECTION"*"tkt.md"*"Goal"*`) and on variables other than `$output`, so the helper set will need to grow to cover those shapes; that growth is the ticket, not a deviation from it.

Whether bash 4+/5 shares this behavior is **unverified** — no other bash exists on the development machine. If it does not, suite strictness is silently machine-dependent, which is the same hazard `setup()`'s `GIT_CONFIG_GLOBAL` shielding already guards against, and worth stating wherever the helpers are explained.

The third acceptance criterion is the load-bearing one: an inert assertion that turns out to be false is a real finding about the code under test, and rewriting it to match current behavior would convert this repair into a fresh silent pass.

## Deviations

- **The helpers moved to a new shared module, `scripts/test_helpers.bash`, rather than being duplicated into both suites.** Approved at the plan gate (a new module is on IMPLEMENTATION-LOOP.md's always-stop list). Duplicating would have put AC5's rationale in two copies free to drift — the contract-drift failure the technical-editor lens exists to catch. Both suites now `load test_helpers`.
- **Added `assert_output_in_order`.** `contract-tamper.bats:63`'s `*"SECTION"*"tkt.md"*"Goal"*"unchanged"*` is an *ordered* match, and four separate `assert_output_contains` calls would silently drop the ordering constraint that assertion exists to pin. This is the helper-set growth the Implementation notes anticipated. The obvious implementation — assembling the arguments into one glob pattern — was tried and rejected: it makes the arguments glob-active, and an expected value of `7:- [ ] a` stops matching the fixture it was written against. Sequential left-to-right consumption with a quoted `case` at each hop keeps every argument literal.
- **Added `test_helpers.bats` (10 tests) as the permanent form of AC2.** The criterion asks only for a one-time falsify-and-revert demonstration; a standing suite additionally stops a future contributor from "simplifying" the helpers back to `[[ ]]`, so AC5's comment is backed by a test rather than trusted. Approved at the plan gate against the narrower reading of the ticket's out-of-scope line. **Corrected at close-out**: five of the ten tests originally ended on a helper call, making the function under test its own judge and contradicting the file's own header claim that assertions there never use the helpers. All ten now take their verdict from a `[ ]`. The residual is stated in the file rather than papered over — a helper stubbed to `return 0` still passes every positive-path test, because an assertion that something succeeds cannot distinguish a working helper from an always-succeeding one; stubbing all three helpers fails tests 1, 3, 4, 6 and 8, so the negative-path cases are what actually pin the mechanism.
- **Converted all 54 `[[ ]]` assertions, not only the 17 inert ones.** AC1 says "regardless of position"; a final-position `[[ ]]` passes today but goes inert the moment anyone appends a line beneath it.
- **The ticket's stated mechanism is wrong, and is corrected in the helper comment rather than in the Goal.** `[[ ]]` does not trip `errexit` *anywhere* on bash 3.2 — not merely inside a function (`bash -c 'set -e; [[ 1 == 2 ]]; echo REACHED'` prints `REACHED`). What makes non-final assertions inert is that a function's status is its last command's; the function *call* is a simple command, which `errexit` does honor. `(( ))` shares the exemption. Single-bracket `[ ]` does not — it is enforced in every position, which is why the 71 non-final `[ ]` assertions were never at risk and why `test_helpers.bats` asserts with `[ ]`. The Goal was left unedited deliberately: `contract-tamper.sh` guards that section, so an in-place correction would make close-out report `Goal changed` and put a spurious tamper warning in front of the reviewer.
- **The counts in the Goal are wrong: 17 of 54 are inert, not 26 of 67.** Measured by parsing each `@test` block for its last meaningful command (contract-tamper `:63,64,99,111,140,153,154,168,169`; materialize-diff `:152,153,204,237,296,316,336,386`). The 26 matches `grep -c '\[\['` on `contract-tamper.bats` alone, three of which are its own doc comment — numerator and denominator appear to have been conflated when `retro.md:13` recorded the figure. The shape of the claim held; the arithmetic did not.
- **The Implementation notes' claim that the suites assert "on variables other than `$output`" is false.** Every one of the 54 converted `[[ ]]` targets `$output`. The non-`$output` assertions are single-bracket `[ ]` and — at `materialize-diff.bats:330` and `:406-408`, two of them non-final — `grep -q`/`grep -qx` against a file. Both forms are simple commands, so both are enforced in every position and the helper set did not need to grow along that axis.
- **Out of ticket scope, user-directed: the repo's verification was configured, and a root `CLAUDE.md` was created.** Added `[verification] command = "bats plugins/pirr/scripts/"` to `.pirr/settings.toml`. The `CLAUDE.md` is not merely resolution source 3, and describing it that way undersold it: three of its lines are verification, and the rest is a standing repo-wide authority surface every session in this repo loads — a layout map, a bare-`[[ ]]` prohibition stated as doctrine, a config-beats-prose precedence rule, and three authoring conventions. Until now no source resolved, so IMPLEMENTATION-LOOP.md's clean-green exit task could never fire and CLOSE-OUT.md's gated merge had no suite to run — this ticket's own close would have merged without running the assertions it just repaired. Requested explicitly after the implementation was complete; declared here because it rides this ticket's diff and would otherwise read as scope creep. Related gap, not fixed here: `/setup`'s `settings.toml` template ships no `verification` knob even though IMPLEMENTATION-LOOP.md names it resolution source 2, which contradicts setup's own "don't omit commented alternatives" anti-pattern.
- **AC2 demonstration, recorded here because the act itself leaves no trace.** `test_helpers.bats` proves the helpers; it does not prove the wiring through `load test_helpers` in the two named suites. So the falsification was also run against the real suites: `contract-tamper.bats:34` had `"SECTION"` replaced with `"DEFINITELY-NOT-PRESENT"` and `materialize-diff.bats:155` had `impl.ts` replaced with `definitely-not-present.ts` — both previously-inert non-final positions. Both tests failed ("unchanged section reports unchanged and emits base text with line numbers", "exit 8 never names a gitignored file"), where before the conversion both would have passed silently. Both edits were reverted and the suite re-verified at 82/82. Surfaced by the spec-conformance lens at close-out, which correctly found the demonstration unrecorded.
- **AC3 outcome: zero findings.** All 17 previously-inert assertions were true — the full suite went from 72/72 to 82/82 green with no assertion needing adjudication. Recorded explicitly because "no findings" is the criterion's honest result here, not a step that was skipped.
