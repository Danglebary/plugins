# Fence-aware contract-section extraction

From ticket 002's refactor pass (security-engineer + qa-engineer, 2× convergence): `contract-tamper.sh`'s section extractor (`section()`, awk boundary `/^## /`) treats *any* line beginning with `## ` as the guarded section's end, with no markdown-fence awareness. If a guarded section (Goal / Acceptance criteria / Approach) contains a `## `-prefixed line — a fenced code example, a quoted second-level heading — extraction truncates there in both base and head, so everything after it is outside the compared window. An author can then rewrite that trailing content on head while leaving the pre-boundary text byte-identical, and the tamper flag reports `unchanged` — silently disarming the alarm the ticket exists to provide.

Latent today: a grep of `docs/specs/**` found zero fenced blocks inside guarded sections, so nothing currently triggers it. But it triggers passively the day any guarded section embeds a `## ` example, and can be actively armed across tickets in a multi-ticket spec — plant a fenced `## ` into the spec's `## Approach` in one ticket, exploit the truncation in a later ticket (base = spec branch, which accumulates prior merged tickets).

Fix shape: make `section()` fence-aware (track ``` / ~~~ toggles; don't treat `## ` inside an open fence as a boundary), or fail safe — force `changed` whenever a captured section contains an in-fence `## `. Either needs a bats fixture: base guarded section with a fenced `## ` line followed by trailing body, head rewrites only the trailing body → must report `changed`. Deferred from ticket 002's refactor pass as a larger extraction change than the pass's other fixes, and latent, so banked rather than re-surfaced fresh each pass.
