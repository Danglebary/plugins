# A merge that lands before verification fails has no stated recovery

`CLOSE-OUT.md`'s gated merge runs the repo's verification **after** merging and deletes the branch only on green. Spec 006's refactor pass closed the naming half of the gap — the command is now resolved per `IMPLEMENTATION-LOOP.md` rather than improvised, and absent/unrunnable degrade exactly as red does, neither deleting the branch. What stays open is the harder question underneath, which that pass deliberately did not answer by fiat.

The loop's degradation rule is written in the loop's vocabulary: *"surface, don't commit."* At the merge gate the commit is already behind the executor — the merge has landed on the spec branch (or the default branch, at `/retro`). "Don't commit" has no referent there. The executor is told to stop and surface, and the merged-but-unverified state simply persists with an undeleted branch beside it. Nothing says whether that merge should be **reverted**, whether the user should be offered the revert, or whether leaving it is correct because a revert is itself an information-destroying act on shared history.

That last framing is why this is not a one-line fix. Under ADR 0004's test, `git revert` (or a reset) of a landed merge is hard to reverse and information-destroying, which makes it a **consent gate** — it cannot be automated, so the fix is necessarily an offer, and offers need a stated resting state and a re-entry route per `RECOVERY.md`. There is also a second-order question: at `/retro` the merge target is the default branch, so a bad merge that stays is visible to anything downstream of it, while at `/done` it is confined to the spec branch. The two consumers may not want the same arm.

Worth deciding alongside: whether verification should move **ahead** of the merge instead. Running it on the ticket branch pre-merge makes the whole question disappear — there is nothing to revert, and the existing "offer, never perform" gate already covers the stop. The cost is that it verifies the pre-merge tree rather than the merge result, so a semantic conflict that merges cleanly and breaks the suite would pass. That trade is the actual decision; the recovery arm above is what's needed only if post-merge verification stays.

Prior art in this repo: `IMPLEMENTATION-LOOP.md:32-35` already states the three-way degradation (absent / unrunnable / red) cleanly for the loop, and `CLOSE-OUT.md`'s decline arm already models "name the resting state, stay re-enterable." Both are the shape this wants.
