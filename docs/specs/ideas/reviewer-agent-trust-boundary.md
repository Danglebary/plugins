# Reviewer agents trust the working tree — base-tree discovery is the Work plugin's problem

From ticket 005's refactor pass (security-engineer). The `standards-reviewer` discovers repo standards from the **working tree** (post-diff state), and its precedence rule lets a documented standard *silence* a baseline smell. So a diff that both trips a smell and adds a `CLAUDE.md`/style-doc blessing that pattern turns off the reviewer's scrutiny of that same diff. `CLAUDE.md` is not a store-artifact path, so the planning-artifact label doesn't cover it. The sibling case (lower severity): `spec-conformance` judges against a spec source (ticket Goal/Acceptance criteria) that the same diff could rewrite.

Latent in the Personal workflow, where the diff author is the trusted user. But reviewer agents are cross-plugin Knowledge-layer surface (ADR 0001), designed for reuse by the planned PR-based **Work plugin**, where the diff author is untrusted — so the weakness is baked into a cross-plugin API now. Not fixed in ticket 005 on YAGNI grounds: hardening base-tree discovery defends against an input the Personal workflow never presents, and ADR 0001 assigns the untrusted-author workflow to a separate future plugin.

Fix shape when promoted (design fresh, don't assume): discover standards from the diff's **base** tree rather than the post-diff working tree, or treat any standards/spec-source file the reviewed diff touches as a finding to scrutinize rather than an authority to obey. Open question at promotion: whether this belongs in the shared reviewer agents (hardening them for both workflows) or in the Work plugin's own dispatch layer (briefing reviewers with a base-pinned standards set) — and whether the decision warrants an ADR recording "the shipped reviewer agents trust the working tree; untrusted-author defense is the Work plugin's job."
