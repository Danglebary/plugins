# A store-map path can carry an executable payload and still get the planning-artifact exemption

`DIFF-MATERIALIZATION.md`'s "Diffs contain planning artifacts" contract labels every hunk under `STORE.md`'s artifact map — `docs/specs/**`, `docs/adr/**`, `docs/spikes/**`, `docs/reviewers.md`, `CONTEXT.md`, `.pirr/settings.toml` — as planning artifacts, **not reviewable code**, and every reviewer brief carries that label. Membership is by path, not content. The exemption is deliberately narrow (it exempts from *code* review only, never from injected-instruction or unexpected-file-shape scrutiny), and for prose artifacts it is exactly right.

`.pirr/settings.toml` is the member that breaks the shape. Spec 006 ticket 006 added `[verification] command`, a shell string that the implementation loop's exit task and `CLOSE-OUT.md`'s gated merge both **execute**, with no confirm gate on the execution itself and no display of the resolved command before it runs. So a change to that one key reaches every reviewer under a label that says "not reviewable code," in a file whose shape is entirely expected, while the same change to a `.sh` or `.bats` file would be code-reviewed. The config's other keys (`merge`, `strategy`, `research_opener`) are read as prose and select among the skill's own arms; this one is different in kind.

`STORE.md`'s config read contract inoculates the wrong half. It says a retired or unknown key and leftover comment prose is "inert: never a refusal, never live instruction" — which covers comments and keys nobody consumes, and says nothing about the **value of a key a skill names and executes**.

Severity in this repo is low and should be stated honestly: pirr is the Personal workflow, where the Glossary already records that the reviewer trust boundary is "latent but harmless… the diff author is the trusted user." Nobody is smuggling a payload past themselves. The finding is structural, and it matters for two reasons that outlive this repo — `work-pirr` forks this corpus and reviews untrusted-author diffs, and the exemption is the kind of rule that gets copied forward without its scope.

Directions worth weighing, not yet chosen. **Extend the base-pinning discipline**: ADR 0005 already has reviewers judge diff-touched *authority* against its base version; the executed verification command is authority of a different sort and could be given the same treatment via `contract-tamper.sh`, surfacing a `changed` verdict. **Display before execute**: have the resolving consumer echo the resolved command before running it, so the merge gate's consent covers what actually executes rather than only the merge. **Carve the label**: state in `DIFF-MATERIALIZATION.md` that store-map keys which are executable payloads are reviewable code notwithstanding their path. The third is the cheapest and the most likely to be forgotten; the second is the one that actually changes what a user sees at the gate.
